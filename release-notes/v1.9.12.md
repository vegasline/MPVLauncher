# MPVLauncher 1.9.12

A batch of fixes, mostly ones a user would have hit without knowing why.

## The Firefox add-on would not load

`extension/manifest.json` declared a background service worker. Firefox does
not implement service workers in Manifest V3 and refuses to load an add-on that
asks for one, so the add-on in this repository could not be submitted to
addons.mozilla.org as it stood. Mozilla's own `web-ext lint` reported it as an
error; it now reports none, and the lint runs on every pull request so it cannot
come back unnoticed.

Two smaller corrections went with it:

- `strict_min_version` moved from 128 to 140. The manifest asks for
  `browser_specific_settings.gecko.data_collection_permissions`, which only
  exists from Firefox 140 — so the old value promised a key the browser could
  not read, and the store rejected it. **Firefox 128–139 is no longer
  supported.**
- `webNavigation` was requested by both manifests the application writes and is
  called by no file. It is gone. A permission the code does not use is one the
  user is asked to grant and the store reviewer has to justify.

## The popup showed `type_mp4`

A media row's type badge asked for the translation `type_<id>` and fell back
with `||`. The translation lookup returns the key itself when it misses, and a
key is a non-empty string — so the fallback never ran, and ten of the twelve
media types rendered as the literal text `type_mp4` in every language.

The same split was hiding files. The popup kept its own short list of stream
types, naming four of them and nothing else, so `mp4`, `webm`, `flv`, `ts`,
`aac`, `mp3` and `ogg` all counted as streams. Turning off the **Streams** chip
therefore hid captured video files along with the streams — the opposite of
what the chip says.

`media_types.js` now owns the vocabulary: one function answers for a type's
label, its colour and its filter category, and a test holds every declared type
to all three.

## Quoted mpv options were split in two

The GUI tokenised the **Extra MPV arguments** setting on spaces alone, so
`--sub-file="my file.srt"` became two arguments and the second half was read by
mpv as an option of its own. Since mpv's `--script` executes code, a value the
user quoted is a value they meant. Both launch paths now share one tokeniser,
and the extension has always had the correct one.

## The window and the toolbar disagreed about where mpv was

Two copies of the install-location list had drifted: the browser extension knew
about `C:\mpv` and `D:\mpv`, the window did not. One person on one machine was
told "mpv was not found" by the window and served by the toolbar.

The search is now the one this project already used for yt-dlp and ffmpeg: the
copy the launcher manages in its own `bin` folder, then somewhere the user's
own mpv turned up, then PATH. The guessed drive-letter locations are gone.

## "MPV started." was never translated

It is the most frequently displayed string in the application, and it was
returned as finished English text, so it reached twelve languages untranslated.
`PlayMedia` now answers in localization keys like the update and
extension-install code always did, and the message exists in all twelve
languages.

## The logo colour picker opened nothing

Eight buttons named a target control with `Tag="TxtColor…"`, and the code-behind
switched on seven names. The eighth fell through to `null`, so the logo colour
swatch did nothing at all. There was no build error and no failing test — the
two lists were simply never compared. A test now compares them.

## Changing the language erased the status line

The translation sweep ended by writing "Ready" over the status line, so
switching language wiped whatever was there — a staged update waiting to
install, a download failure, a relaunch error. The status line is transient
state rather than a label; it is now set where the window loads and left alone
by the sweep.

## Removed

Handlers and members that nothing reached. `get_filter_defaults` and
`apply_filter` in the background page had no sender; `apply_filter` was the only
caller of a filter predicate, which existed in two copies that disagreed about
what to do with an unrecognised type — and the copy that actually ran was the
one the test suite could not execute. Six dead C# members went with them.

The host-permission flow is **still present** and still tested: the popup does
not yet offer the button, and the test suite names that gap explicitly so it
cannot grow unnoticed. It was left alone because deleting a working capability
is a product decision, not a refactor.

## Testing

The project had no C# tests at all, and could not have had them: the on-disk
layout was a static, process-wide latch rooted in the OS profile, so the
application could not be pointed at a scratch directory. That layout is now a
value you can substitute, and there is a suite of 65 tests covering it — which
is what made the four behavioural bugs above reproducible in the first place.

| Suite | Before | After |
|---|---|---|
| Extension | 166 | 250 |
| C# | 0 | 65 |
| Locale | 40 | 40 |
| `web-ext lint` errors | 1 | 0 |

The extension suite gained a check that every message handler has a sender, so a
handler nobody calls now fails a test instead of waiting to be noticed. It had
already been written down once, after `clear_network_media` had the same
problem.
